# 開発方針：Lawnchair への機能追加とメンテナンス

本ドキュメントは、Lawnchair プロジェクトをフォークし、独自の機能追加を行いながら、元プロジェクト（Upstream）の更新を円滑に取り入れるための開発指針をまとめたものです。

## 1. Git 管理戦略：Upstream との同期

元プロジェクトの変更を常に取り込める状態を維持し、競合を最小限に抑えます。

### リモート設定
`origin`（自身のフォーク）に加え、元リポジトリを `upstream` として登録します。
```bash
git remote add upstream https://github.com/LawnchairLauncher/lawnchair.git
```

### ブランチ運用
- **`16-dev` (またはベースブランチ)**: `upstream` の最新状態を反映させるためのクリーンなブランチ。直接の作業は行わず、`upstream` からのプルのみに使用します。
- **`feature/custom-[機能名]`**: 独自の機能追加を行うための作業ブランチ。必ず `16-dev` から分岐させます。

### 同期手順（Rebase の推奨）
作業ブランチを最新の状態に保つため、`merge` ではなく `rebase` を活用します。
1. `16-dev` を最新にする: `git checkout 16-dev` -> `git pull upstream 16-dev`
2. 作業ブランチを最新の上に載せ替える: `git checkout feature/custom-xxx` -> `git rebase 16-dev`

---

## 2. コード管理指針：保守性と独立性

将来的な `upstream` の更新（リベース）を容易にするため、元のコードへの変更を最小限に抑えます。

### パッケージの使い分け
- **`lawnchair` パッケージ**: 独自のロジック、UI、新規クラスは基本的にここに追加します。
- **`src` パッケージ**: `Launcher3` 由来のコード。ここへの変更は必要最小限に留めます。

### 実装のベストプラクティス
- **新規クラスの優先**: 既存ファイルを肥大化させず、新しいクラスを作成して既存コードからはフックを呼ぶ形にします。
- **変更箇所の明示**: やむを得ず既存コードを修正する場合は、コメントで範囲を明示します。
  ```kotlin
  // START CUSTOM: [機能名] のための追加
  val myCustomValue = ...
  // END CUSTOM
  ```
- **依存性注入 (DI)**: Dagger などの既存の DI 仕組みを活用し、コンポーネントを疎結合に保ちます。

---

## 3. 品質指針
- **KISS 原則**: 最も単純で意図が明快な実装を心がけます。
- **ボーイスカウト・ルール**: 触れたコードは「来たときより綺麗に」しますが、指示のない範囲の破壊的変更は避けます。
- **日本語コメント**: 技術的慣習に反しない限り、意図を明確にするために日本語で簡潔なコメントを記述します。
